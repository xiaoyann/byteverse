## 起因

配置中心的 schema 想同时做到两件事：**保留字面量类型**，又**校验结构合法性**。于是用了 `satisfies`。

```ts
type FieldType = 'string' | 'number' | 'boolean';

const schema = {
  title: { type: 'string' },
  count: { type: 'number' },
} satisfies Record<string, { type: FieldType }>;
```

看起来没问题，但下游需要拿到 `schema.title.type` 的**字面量类型** `'string'` 时，拿到的是 `FieldType`。

## 原因

`satisfies` 只做「可赋值性检查」，不做类型收窄。对象字面量的属性默认会被拓宽（widening），`'string'` 变成 `string`，再被 `satisfies` 的上下文类型拉成 `FieldType`。

正确的写法是加 `as const`：

```ts
const schema = {
  title: { type: 'string' },
  count: { type: 'number' },
} as const satisfies Record<string, { type: FieldType }>;

// 现在 schema.count.type 的类型是 'number'
```

顺序不能反，`satisfies ... as const` 是语法错误。

## 两处反例

### 反例一：函数返回值

```ts
// ❌ 返回类型被拓宽，调用方拿不到字面量
function getConfig() {
  return { mode: 'dark' } satisfies { mode: string };
}

// ✅
function getConfig() {
  return { mode: 'dark' } as const satisfies { mode: string };
}
```

### 反例二：路由表

```ts
// ❌ path 被推成 string，Link 的类型校验就没了意义
const routes = [{ path: '/daily' }, { path: '/about' }] satisfies Route[];
```

这种场景其实更该用 `as const`，因为我们要的恰恰是字面量的联合类型 `'/daily' | '/about'`。

## 判断标准

我记了三条：

1. 下游要**字面量类型**（联合类型推导、模板字符串匹配）→ 用 `as const satisfies`
2. 下游只要**结构校验**（保证字段齐全、类型正确）→ 单独用 `satisfies`
3. 需要**可变**（后续要 push / 修改）→ 不能用 `as const`，改用显式泛型标注

## 一个小收获

> `satisfies` 的价值在于「检查但不改变推断结果」。如果发现加了它之后类型反而变宽，八成是漏了 `as const`。
