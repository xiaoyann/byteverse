## 背景

某跨端页面的首屏（首次内容渲染）稳定在 1.8s 左右，业务方希望压到 1s 以内。压测环境数据一致，可以放心做对照实验。

## 耗时拆解

用容器侧的打点把整条链路切开：

| 阶段 | 耗时 | 占比 |
| --- | --- | --- |
| 容器初始化 | 420ms | 23% |
| JS Bundle 下载 + 解析 | 610ms | 34% |
| 首屏接口请求 | 480ms | 27% |
| 渲染 + 布局 | 290ms | 16% |

结论很清楚：**下载解析和接口请求是两条可以并行的时间线，但现在被串行了**。

## 三个层次的预加载

### 容器层预加载

在容器启动时就发起首屏接口请求，交给业务侧消费。

- 收益：省掉 480ms 的串行等待，是目前最大的一笔
- 风险：容器不知道业务需要什么参数，容易预加载错；需要设计「预加载结果有效期」，否则用户停留久了会拿到脏数据

### 路由层预加载

路由跳转前预取目标页面的 JS chunk。

- 收益：把 chunk 下载提到点击瞬间之前，感知上更快
- 风险：弱网下会抢占当前页面的带宽，反而拖慢当前交互

### 业务层预加载

在页面 `useEffect` 里提前请求第二屏数据。

- 收益：滚动体验更顺
- 风险：几乎无，但收益也最小，属于优化末端

## 最终方案

采用了 **容器层预加载 + 路由层预取** 的组合，业务层暂时不动。

```ts
// 容器侧：启动即发起，带 30s 有效期
const prefetch = container.prefetch('/api/home/feed', { ttl: 30_000 });

// 业务侧：命中就用，未命中再自己请求
const data = await prefetch.consume() ?? await fetchFeed();
```

线上结果：

- 首屏 1.8s → **0.9s**（P50）
- 首屏 2.9s → 1.6s（P90，弱网改善更明显）
- 接口 QPS 上升 12%，可接受

## 反思

预加载的本质是 **用带宽和请求量换时间**，不是免费的。决策前必须先回答两个问题：

1. 这个页面的流量结构里，弱网占比多少？（弱网下预加载可能反向恶化）
2. 预加载失败时的降级路径有没有写？（必须有，否则就是单点故障）
