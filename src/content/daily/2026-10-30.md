## 现象

`npm run build` 之后，产物里有一个 `vendor-*.js` 达到 **380KB（gzip 后 121KB）**，明显超出预期。首屏指标里 LCP 是 2.4s，怀疑和它有关。

## 定位过程

先装可视化插件：

```bash
npm i -D rollup-plugin-visualizer
```

```ts
// vite.config.ts
import { visualizer } from 'rollup-plugin-visualizer';

export default defineConfig({
  plugins: [
    react(),
    visualizer({ filename: 'dist/stats.html', gzipSize: true, open: false }),
  ],
});
```

打开 `stats.html`，一眼看到罪魁祸首：`lodash` 占了 71%。

问题代码只有一行：

```ts
import { debounce } from 'lodash';
```

看起来是按需引入，但 `lodash` 的 CommonJS 入口无法被 Rollup 静态分析，**整包都被打了进来**。

## 三种解法对比

| 方案 | 产物体积变化 | 迁移成本 | 结论 |
| --- | --- | --- | --- |
| 换成 `lodash-es` + 具名导入 | 380KB → 268KB | 低 | 可用但不够干净 |
| 换成 `lodash/debounce` 子路径导入 | 380KB → 262KB | 低 | 可用 |
| 手写一个 12 行的 debounce | 380KB → 259KB | 低 | **采用** |

顺手检查了一下，项目里只用到 `debounce` 和 `throttle` 两个函数，其他依赖全是「历史遗留」。

```ts
export function debounce<T extends (...args: never[]) => void>(fn: T, wait = 300) {
  let timer: ReturnType<typeof setTimeout> | undefined;
  return (...args: Parameters<T>) => {
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => fn(...args), wait);
  };
}
```

## 结果

- `vendor` chunk：**380KB → 259KB**（gzip 121KB → 82KB）
- 首屏 LCP：2.4s → **1.9s**
- 构建时间：没有明显变化

## 反思

> 体积问题往往不是「某个库太大」，而是「引入了整个库却只用了一个函数」。

后续想加一条 CI 卡口：单 chunk 超过 250KB 就构建失败并提示看 `stats.html`。不然这类问题只会反复出现。
