## 为什么值得做

写日报本身不痛苦，痛苦的是「写完还要复制粘贴、调格式、改日期、发布」。任何超过三步的手工流程，最后都会变成三天打鱼两天晒网。

所以今天只做一件事：**把归档动作压缩到一条命令**。

```bash
npm run daily:import -- ~/Downloads/workbuddy-2026-10-31.md
```

## 三个设计决策

### 1. 内容用 Markdown，不用数据库

日报是低频写入、高频读取、几乎不修改的内容。上数据库意味着要维护一个后端，收益却只有一个「在线编辑框」。而 Markdown 文件：

- 天然带版本历史，`git log` 就是内容变更记录
- 可以全文检索、可以 diff、可以离线写
- 构建时静态生成，零运行时成本

代价是不能在网页上直接编辑。接受。

### 2. 索引不落盘，用构建期扫描

一开始我打算维护一个 `index.json`，每次新增文章手动注册。后来改成 Vite 的 `import.meta.glob`：

```ts
const rawModules = import.meta.glob('../content/daily/*.md', {
  query: '?raw',
  import: 'default',
  eager: true,
});
```

文件即索引。新增文章只需要丢一个 `.md` 进去，列表页、归档、标签统计全部自动更新，永远不会出现「文件在但列表里没有」的经典事故。

### 3. 导入脚本负责「补齐元信息」

WorkBuddy 导出的内容通常只有正文，缺 frontmatter。脚本做四件事：

1. **日期**：优先取文件名里的 `YYYY-MM-DD`，其次正文首个日期，最后用当天
2. **标题**：优先取正文第一个 H1，然后把它从正文里剥掉（避免详情页标题重复）
3. **摘要**：取第一个有效段落，去掉 Markdown 标记后截断到 96 字
4. **标签**：从 frontmatter 或 `--tags` 参数读，都没有就给默认值

这样导出文件几乎是「零整理成本」直接可用，需要精细控制时再手动改 frontmatter 覆盖。

## 流水线现状

```text
WorkBuddy 生成  →  导出 .md  →  daily:import  →  git commit  →  部署
                      ↓             ↓
                   原样保留      补 frontmatter + 改名 + 落盘
```

## 踩到的小坑

- 导出文件是 CRLF 换行，frontmatter 的正则得先做 `\r\n → \n` 归一化，否则 `---` 匹配不上
- 有些导出文件开头带 `\uFEFF` BOM，会让第一行判断失效
- 标题里带冒号时，YAML 不加引号会解析失败，所以写入时统一用单引号包裹
