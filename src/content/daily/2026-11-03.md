## 今日概览

截至今天 21:30（UTC+8），最值得看的一件事不是新模型，而是一篇**被当场拆掉的论文式发布**：MIT CSAIL 的「权重空间编程」昨天在 HN 冲到 2800 分，今天就被 spaCy 作者 Matthew Honnibal 用一张实验对照表指出，那个被当作标题的 Qwen 实验根本没有「只读原始权重」。

同样在今天摊开的还有账本：Anthropic 修订招股书，首次给出 Q3 数据——单季 170 亿美元营收，同时 8954 亿美元的采购承诺。一边是研究人员在给模型能力打补丁式地降级，一边是厂商在给未来几年的算力开支签字，这两件事放在一起，构成了今天的主线：**能力宣称和资本承诺都在加速，但可验证的部分没有跟上。**

- **[OccupySaaS：被裁的工程师用 AI 重建闭源 SaaS](https://occupysaas.com/)**（项目官网，10 月建立｜HN 516 分，11-02）

- **[GitHub Actions 将从 12 月 2 日起默认封禁 pull_request_target](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2)**（GitHub Changelog，11-02）

  `pull_request_target` 在基仓库上下文中运行、能读到 secrets，一旦工作流执行了来自 fork 的不可信代码，就等于把密钥递出去。GitHub 的原计划是 11 月 2 日执行，现在推迟到 12 月 2 日，并安排两次「brownout」实际演练：11 月 9 日和 11 月 16 日的 16:00–18:00（UTC），这两个窗口内被规则拦下的运行会直接失败并给出错误注解，窗口结束后回到 evaluate 模式（只警告不拦）。

  影响范围是所有公开仓库（Free、Team、Enterprise Cloud），私有与内部仓库、Enterprise Server 不受影响。现在就可以在 Insights 里看规则会拦掉哪些运行，再决定是保留默认拦截，还是在 Actions event policy 里显式放行特定工作流文件。如果你维护开源项目又用这个触发器做自动化，这周的 brownout 就是免费的压力测试。

- **[Ubuntu LTS 内核仍缺 CVE-2026-98432 修复](https://ubuntu.com/security/CVE-2026-98432)**（Ubuntu 安全公告页，10-15 发布、11-03 更新｜社区整理见 [freenode.net](https://freenode.net/article/ubuntu-lts-kernels-still-unfixed-for-critical-cve-2026-98432)，10-31；HN 561 分）

  这是一个 IPv4 TCP 的 use-after-free：`tcp_v4_syn_recv_sock()` 把 `ireq_opt` 的所有权转给子 socket 却不复制，另一个 CPU 在处理重传 SYN 时仍会在 RCU 读锁下读同一块内存，最终在 `ip_options_build()` 里踩到已释放对象。Ubuntu 安全团队在页面上写明「可导致远程代码执行」，优先级 Critical，CVSS 9.8。

  官方页目前给出的仍主要是缓解手段（用 nftables 过滤 IPv4 options，代价是放弃 IP options），我在页面上没有确认到已发布的修复内核；freenode.net 10-31 的整理称 22.04、24.04、26.04 三个 LTS 都没有可用补丁。同期 HN 上另有一条 1,500 分的「WTF Ubuntu?」讨论，情绪指向的是发布流程而非单个漏洞。自建机器跑公网服务的，本周值得亲自核一遍自己内核版本对应的公告。

- **[vercel-labs/agent-desktop：让 agent 通过无障碍树操作桌面](https://github.com/vercel-labs/agent-desktop)**（GitHub / Vercel Labs，11-03 见 Trending）

  解决的是「computer use 靠截图像素匹配」这个笨办法：它读取操作系统的 accessibility tree，把当前界面反射成一份 JSON，每个可操作元素带一个 ref；agent 对 ref 下指令，再取一次快照确认结果，循环留在你自己的 agent 里，不在工具内部。CLI 形式，每次调用独立进程，`npm i -g agent-desktop` 安装，附带 x64/ARM64 原生二进制；headless 模式下明确禁止把窗口提到前台、禁止合成输入。

  平台差异要提前知道：macOS 需要授予辅助功能权限（`agent-desktop permissions --guide`），Windows 对同完整性级别的应用无需授权，Linux 需要图形会话加 `at-spi2-core`。官方同时提醒快照、剪贴板、截图都可能包含隐私内容，别进公开日志。另外可选的 JEV helper 会把屏幕描述发给配置的模型服务商，与 CLI 本体是分开的——这条决定了它到底算本地工具还是云工具。Homebrew 与 Scoop 官方包仍在提交中。

## AI 技术

- **[「权重空间编程」：模型直接读写神经网络权重](https://rikiyat.github.io/blog/weight-space-programming/)**（MIT CSAIL，11-02｜HN 2,843 分）

  论文主张前沿 LLM 已经能原生理解并改写权重，不走梯度下降：只给 17,253 个原始权重，GPT-6 Astra 能以 99% 置信度判断这个 MLP 是玩 Breakout 训练出来的；对一辆永远过不了障碍的车，一次性改 3.5% 的权重，成功率从 0% 到 100%；最抓眼球的是 Qwen3.5-0.8B——Astra 找出导致推理循环的权重问题，只改 0.016% 的权重，MATH-500 从 7.9% 升到 48.1%，IFEval 提升 3 倍。

  如果这些成立，含义是优化器的地位被削弱：过去几年我们用 LLM 优化 prompt、代码、harness，理由是「权重没法用文字优化」，这篇试图推翻这个前提。作者也承认这是早期结果，且全程没有让 Astra 写训练循环。**但「只读原始权重」这个前提本身，今天被公开质疑了，见下一条。**

- **[《Astra 读写权重改进 Qwen》这篇发布严重误导](https://honnibal.dev/blog/astra-read-write-misleading)**（Matthew Honnibal，11-03）

  spaCy 作者把原文的 8 组实验逐条列成表，标出三列：是否只读原始权重、是否需要 Python、是否真的运行了网络。结论很硬：真正「裸读原始浮点数、不用工具、不跑网络」的只有实验 1、2、4，规模 17K–172K 权重；**所有涉及真实语言模型的实验都用了 Python，而被当作标题的 Qwen 实验还额外跑了最多 50 批练习题**。至于从零写 MinAtar 游戏网络，权重起点是零，「没什么可读」；9×9 围棋网络则要跑 0–50 个 pass 才达标。

  他的比喻是魔术师：每次换一种手法，观众以为只有一种，于是每次「推翻」都像在验证。真正被证明的是「Astra 能被提示去设计并执行人类 ML 工程师会做的分析和改权重脚本」，这本身不弱——一两年前的模型做不到——但它和「模型原生理解权重」是两种能力，被塞进了同一篇里。这条对我的直接用途是方法论：**看到「只靠 X 就做到 Y」的发布，先找实验表里那一列「是否真的只用了 X」**。

- **[Anthropic 用 Claude 把 Messages API 从 Python 迁到 Rust：CPU 省 40%–50%](https://www.infoq.cn/article/IMWM7ZXDi99sMiUVZBIF)**（InfoQ 中文，11-03 整理｜原始访谈为 Latent Space 播客 10-27）

  平台工程负责人 Katelyn Lesse 的说法：团队里一个 Rust 开发者都没有，仍然决定一次性重写整个 Messages API，人负责系统设计与迁移计划，Claude 负责实现，然后导入影子流量对比 Python 与 Rust 两套输出，再逐步切真实流量。结果 CPU 降 40%–50%，首 token 延迟改善 10%–20%，长任务改善更明显。她强调这是一次纯移植，刻意不加新功能；迁移小组用静态分析跟进其他团队在 Python 版上新增的功能。

  两个提醒。一是这些数字是访谈里的口头估算（ballpark），不是 Anthropic 发布的基准测试，也没有官方工程博客复述，当量级看就好。二是「零 Rust 经验」是起点不是全程——现在团队成员基本都自认是 Rust 工程师，中途也补招了有经验的人。真正可复用的是流程：先建裁判（能同时评估新旧代码的测试），再写规则手册，小样试跑后把代码丢掉只留规则，影子并跑再灰度。

- **[CoworkOS：把「任务策略」和「执行管理」拆开的长期协作 harness](https://huggingface.co/papers/2611.03178)**（HF Daily Papers，11-02｜80 赞）

  面向长时间、多人机协同的生产力任务（文档、演示、CAD、Blender 场景），核心设计是把决策权留给模型、把状态与反馈留给运行时：模型决定做什么、委派给谁、是否验收，运行时维护状态机与反馈回路。三层架构支持同步或异步分派给 Subagent，人和 agent 通过共享应用层编辑同一份不断变化的对象，而不是各自维护副本再合并。

  这解决的是 cowork agent 最容易崩的地方——长任务里上下文漂移和验收标准丢失。对做 agent 应用的人，值得看的是它把「谁有权接受结果」显式建模，而不是塞进 prompt。论文本身未给出与商业产品的对比数据，属于架构提案加初步实验。

- **[CUA-Master：用开放世界数据飞轮训练 computer-use agent](https://huggingface.co/papers/2611.03126)**（HF Daily Papers，11-02｜57 赞）

  针对 CUA 训练数据的三个短板——多样性、可控性、可靠性——提出嵌套双环：外层是「世界数据模型」飞轮，持续吸收开放语料，并用当前模型的弱点反向指导下一轮数据构造；内层用教学视频挖真实工作流作为种子任务，再做视觉与语义双路径扩展。相比依赖自生成经验做递归改进的路线，它试图让每一轮的数据来源都在模型能力之外。

  限制也很清楚：这类飞轮的收益高度依赖种子数据质量与评测环境，论文的对比集中在自家流水线内部。若你在做浏览器/桌面自动化，这篇的价值是数据构造思路，不是现成可用的模型。

- **[CrossSWE：跨仓库联合开发基准](https://huggingface.co/papers/2611.01484)**（HF Daily Papers，11-01｜19 赞）

  现有 coding agent 基准基本都在单仓库里加长、加难，但真实开发常常横跨多个互相依赖的仓库，难点是依赖推理、变更传播和接口一致性。CrossSWE 收了 171 个真实实例、165 个仓库、20 个技术域、13 种语言，并且用「只改一个仓库是否无法达成目标行为」来验证任务确实需要协同修改。

  对五个 LLM 的评测显示这类任务依然很难，具体分数不同模型差异明显（摘要只给趋势，未逐项列出）。如果你在评估 coding agent，这个基准补上了「跨仓库」这一维——也是多仓 monorepo 之外最常见的真实形态。

- **[Wave Forcing：把流式视频生成压到「一轮前向出一个 chunk」](https://huggingface.co/papers/2611.00859)**（HF Daily Papers，10-31｜93 赞）

  实时长视频生成的老问题是效率：chunk 级自回归即使一步去噪，串行去噪加历史缓存刷新仍要两次前向，rollout 越长越容易画质退化、镜头漂移。Wave Forcing 把生成、训练、执行一起设计：用 chunk 级因果注意力让当前 chunk 能读到更早、更干净的 chunk，再把错开的去噪与缓存刷新分配到多个模型副本上，做到流水线填满后每个并发前向轮次产出一个 chunk。

  对我的用途是判断「实时视频」这件事的工程成本：它优化的是吞吐与长序列稳定性，不是画质上限；配套的三阶段训练流程也说明这类模型不能直接拿现成权重改。属于方法论文，尚无公开可试的权重说明。

## 大前端与后端

- **[Cloudflare 把 DNS 构建从「全量重建」改成「证明安全的最小构建」](https://blog.cloudflare.com/dns-targeted-zone-builds/)**（Cloudflare Blog，11-02）

  背景数字很能说明问题：Zone Builder 现在每秒接收约 700 条 DNS 记录变更（2022 年是 250 条），再加约 100 个其他事件；单个 zone 已出现超过 2,000 万条记录，预期将来会到亿级。问题不在事件数量，而在「区域设置变更会重建整个 zone」——一次设置改动就要把上千万条记录重新转换成 Quicksilver 的键。

  做法是加一个构建规划器：对每个区域事件算出「能证明安全的最小构建范围」，再由新调度器把同一 zone 的工作合并。难点不在写代码而在证明——记录事件能说明改了什么，设置事件往往不说明原因，还可能影响同名 zone 共享的数据。结果是全量构建减少 40%、峰值内存降 85%，省出的余量让管道把「为容错而保留的等待时间」砍半，DNS 变更到写入 Quicksilver 的时间减半。这类文章的价值在于它把「缓存/构建粒度」这个老话题的证明成本讲清楚了。

- **[Vercel 在构建前后拦截恶意 npm 包](https://vercel.com/changelog/blocking-malicious-npm-packages-before-and-during-installation)**（Vercel Changelog，11-02）

  两道检查：安装前扫 lockfile（包括从构建缓存恢复依赖的场景），安装中拦截对已被标记的公开 npm 包的下载；名单按具体版本（version-level）维护，新规则通常几分钟内进入新构建。命中后部署直接失败，错误里给出包名与版本，并尝试让受影响的构建缓存失效。所有套餐自动生效，无需配置。

  这条对前端项目尤其相关：`postinstall` 脚本是供应链攻击最常用的落点，而 lockfile 一旦被污染，本地和 CI 都会一起中招。注意它只覆盖 Vercel 上的构建，本地 `npm i` 仍然要靠自己的策略。

- **[Vercel 把 Data Cache 并入 Runtime Cache，并开始按量计费](https://vercel.com/changelog/data-cache-is-moving-to-runtime-cache)**（Vercel Changelog，10-30）

  Data Cache 退出 beta，成为 Runtime Cache 的一部分：Next.js 的 `fetch` 缓存与 `unstable_cache` 在所有版本上无需改代码即自动切换，`use cache: remote` 本来就走这套 API。容量上 Pro 每个项目/环境独立分配，是原先团队共享池的 8 倍，Enterprise 是原来的 10 倍。

  要留意的是计费：原先不计费的 Data Cache 读写，迁移后按 Runtime Cache 价格收费，读 $0.40/百万单位、写 $4.00/百万单位起（按区域浮动）；Hobby 每月 1 百万读 + 20 万写免费额度，Pro 从每月 20 美元基础设施额度里扣。10 月 30 日及之后新建的团队默认就是新方案，已有团队 Hobby 在 11 月 29 日迁移，Pro 会另行通知日期。**这意味着缓存策略第一次直接变成账单数字**，迁移前值得先去 Observability 看读写量。

- **[Supabase 发布 DBArena：可复现的托管 Postgres 基准](https://supabase.com/blog/introducing-dbarena)**（Supabase Blog，10-30）

  对比 Supabase Postgres（默认存储与 OrioleDB 两种）、Amazon RDS、Google Cloud SQL，统一 Postgres 17、按 vCPU 匹配、磁盘 IOPS 与吞吐对齐、各家保持默认配置、客户端直连不走连接池。每个档位跑两种场景：数据集能放进内存（缓存命中率 ≥99%）和数据集是内存的 4 倍（强制读盘）。指标三个：tpm、tpm/$（按公开按需价，不打折）、p95 延迟。原始数据文件含完整命令与配置，可自行复跑。

  必须说清楚的立场问题：**Supabase 是 DBArena 的赞助方**，比较对象里包含自家产品。方法论公开、工具开源、可复跑，这三点让结论可检验，但「谁来选场景」仍然由赞助方决定。当作方法论样本读，比当作选型结论读更安全。
