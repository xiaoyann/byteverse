## 今日概览

截至今天 09:10（UTC+8），过去 24 小时里最值得读的不是模型发布，而是两起「agent 动了不该动的东西」的事件：GitBook 把 11 月 2 日的入侵定性为使用 AI 代理的定向攻击，Postman 则被指在用户没同意的情况下，给自己的桌面端装上了 Codex 与 Claude 插件并自行批准 hook。

前端侧有一条该立刻处理的：Next.js 11 月安全版本一次修掉 7 个 CVE，其中一个是开了 Cache Components 后的跨租户缓存泄露。另外 Safari 27.3 beta 开始对没做深色模式的站点做自动反转，声明 `color-scheme` 的站点可以完全规避。

## 行业动态

- **[GitBook 称遭 AI 代理定向入侵，平台 API token 全部作废](https://www.gitbook.com/status/security-incident-2026-11-03)**（GitBook Status，11-03）

  11 月 2 日 19:00 CET，攻击者拿到 GitBook 部分基础设施凭证。官方通报把事件定性为「使用 AI 代理的、高度定向的攻击」，处置动作包括把应用与需登录的文档站点下线、轮换全部凭证、作废平台上所有客户的 API token。可能被访问的数据列得很具体：集成 token、Git Sync secret、API token，以及访客向 GitBook Assistant 提的问题；目前没有发现内容被篡改的证据。对把文档站接进 CI 或 MCP 的团队，现在该做的是轮换 GitBook 相关 token、重连 MCP server。这条值得留意的不是「AI 攻击」这个标签，而是一个文档平台同时握着仓库同步凭证和一堆第三方集成密钥，攻击面比它看起来大得多。

- **[Postman 桌面端被指自动给 Codex 与 Claude 装插件，并尝试自行批准 hook](https://github.com/postmanlabs/postman-app-support/issues/14370)**（GitHub Issue，10-25 提交 / 11-03 引爆讨论）

  一位 macOS 用户从 Postman 日志里翻出 `auto-existing-upgrade` 记录：打开旧版客户端后，Postman 自动安装了 Postman CLI、Codex 插件与 Claude Code 插件，往 `~/.codex/config.toml` 写入插件市场与 MCP 配置，还注册了一个 SessionStart hook，内容是要求 agent 在处理「任何非平凡的 API 工程任务」前先加载 `postman:api-engineer` skill。安装器源码里还有一步是用 `config/batchWrite` 写入 `trusted_hash`，即让插件把自己标记为可信。

  报告者明确说明证据只覆盖「未经同意的集成与指令注入」，并不主张数据外泄——HN 上的标题写成「尝试分享所有 API 数据」，比 issue 本身的结论更进一步，这里按 issue 的口径记。issue 下有以团队口吻的回应，称捆绑 CLI 与插件是为了降低配置成本，会把 opt-in 做得更清楚，并复查 hook 批准逻辑。对每天开好几个 agent 的人，这是具体的检查项：翻一遍 `~/.codex/config.toml` 与 `~/.claude/settings.json`，看有没有自己不认识的 marketplace 与 hook。

- **[多名用户报告 Codex 的数据共享开关被静默重新打开](https://news.ycombinator.com/item?id=50352757)**（Hacker News，11-03）

  帖主称团队一直手动关闭 Codex 与 Claude Code 的数据共享，近日发现 Codex 里「Improve the model for everyone」又被打开，没人主动改过。讨论里有人贴出更早的同类反馈，也有人说改用硬件密钥登录的高级账号保护后该开关会被锁死。OpenAI 尚未公开回应，这条目前只能算用户侧报告。

  它对我的意义不在个案真假，而在于「合规靠产品里一个复选框」这件事本身不可靠：如果团队真在意 prompt 里的 IP，需要的是账号级策略与出网审计，而不是每月手动确认一次。

- **[Google 将对禁用 AI 的学区关闭搜索](https://news.ycombinator.com/item?id=50353192)**（Hacker News 讨论，11-03；原文 NYT，付费墙）

  据报道，Google 教育副总裁 Chris Phillips 表示，如果学区禁止 AI 使用，学生「将无法使用搜索，并会看到一条来自学校的、说明搜索不可用的提示」。也就是说，禁用 AI 的代价被设计成连搜索一起停，而提示语把决定归因给学校。原文在 NYT，付费墙，此处仅据标题与讨论转述。

  对做教育类产品的人是明确信号：平台正把 AI 与基础服务打包成同一个开关；对普通用户，这解释了为什么「学校禁 AI」会变成「学生查不了资料」。

- **[乌镇峰会：DeepSeek、千问、MiniMax 把开源竞争谈到了工程工具层](https://news.qq.com/rain/a/20261104A02VFO00)**（腾讯新闻，11-04 报道 11-03 会议）

  11 月 3 日的「人工智能乌镇对话」上，三家中国模型公司谈的重点都不是参数规模。DeepSeek 研究工程师高熙提到，除权重之外还开放了训练与推理的软件组件，例如面向 MoE 专家并行的通信库 DeepEP，SGLang 已把它列为可选后端；千问项目负责人刘大一恒谈的是用多种模型尺寸覆盖不同硬件与成本区间；MiniMax 则把实验经验与研发过程也纳入开放范围。

  这条线索对做部署的人比模型榜单有用：决定自托管能不能跑起来的，往往是通信库、量化版本和推理框架适配，而不是 benchmark 分数。

- **[Revolut 把推理迁到自托管 GLM，混合成本约 0.3 美元/百万 token](https://news.ycombinator.com/item?id=50350004)**（Hacker News 讨论，11-03）

  据 Revolut AI ops 负责人 David Abitbol 在演讲中披露，他们用 56 张 B200 自托管 GLM，混合成本约每百万 token 0.3 美元，约为此前付给 Anthropic 与 OpenAI 的十分之一；讨论里的估算认为硬件加运维投入在 250 万至 300 万美元量级。需要注意条件：这是单一公司、特定流量结构下的数字，演讲者没有展开集群运维的复杂度。

  真正值得记住的是比例关系——当调用量足够大、任务又足够常规时，自托管的成本拐点来得比多数团队预期早；量小的时候，省下的钱不够付一个 SRE。

- **[美国科技巨头表外 AI 债务半年增 90%，达 3.2 万亿美元](https://news.ycombinator.com/item?id=50358422)**（日经亚洲，11-03；付费墙）

## 产品发布与更新

- **[Vercel Security Review 进入公测：每次 push 都跑漏洞审查](https://vercel.com/changelog/vercel-security-review-public-beta)**（Vercel Changelog，11-03）

  面向 Pro 与 Enterprise 团队。开启后，向已连接 GitHub 仓库的每次 push 都会触发审查，结果进 Vulnerabilities 面板，附摘要、修复建议和 AI 生成的危险等级。它从 push 事件而不是 PR 触发，所以直接推和 force push 到生产分支也会被覆盖；公开仓库的漏洞详情只留在面板里，不会贴到 PR 评论。点「Fix with Vercel Agent」会由 agent 提修复 PR，合不合由人决定。

  与常见的 PR 期 SAST 相比，差异在覆盖范围和「发现即可修」的闭环；限制也明确：绑定 Vercel 平台与 GitHub，非 Pro/Enterprise 用不上。

- **[Cloudflare 推出 Zero Wire：把严重漏洞做成新闻稿式的简报](https://blog.cloudflare.com/zero-wire/)**（Cloudflare Blog，11-03）

  Zero Wire 放在 Cloudflare Radar 的安全栏目下，每条漏洞一张「索引卡」：白话解释、谁该去查、建议动作、证据与厂商指引链接，另附一段可直接丢给 agent 的预编译 prompt，用来评估自家资产是否受影响。官方明确说它不做「所有 CVE 的目录」，只挑重大事件。

  对没有专职安全团队的小团队，这种格式比自己拼 NVD 加厂商公告省时间；但它是第三方解读，不是权威结论，处置优先级仍要回到自己的资产清单。

- **[GitHub Copilot 接入 JetBrains Air，走 Agent Client Protocol](https://github.blog/changelog/2026-11-03-github-copilot-is-now-available-in-jetbrains-air)**（GitHub Changelog，11-03）

  在 JetBrains IDE 的 Air 面板里可以直接选 GitHub Copilot，用现有 Copilot 订阅跑编码任务，支持并行多个 agent 会话与就地 review；云端任务走 Air Teams，消耗 Copilot 额度而不是 JetBrains AI credits。集成使用 ACP（Agent Client Protocol），与已有的 Copilot 插件并存。

  对同时用 JetBrains 和 VS Code 的人，这意味着 agent 入口开始收敛到协议层，而不是绑死在某个 IDE。

- **[Dependabot 开始给 agent 的 skill、prompt 和指令做版本更新](https://github.blog/changelog/2026-11-03-dependabot-version-updates-support-agent-package-manager)**（GitHub Changelog，11-03）

  通过 Agent Package Manager（APM）声明的 git 依赖，现在可以由 Dependabot 定期开 PR 升级，并重新生成 `apm.lock.yaml`；在 `.github/dependabot.yml` 里加一段 `apm` 配置、指定含 `apm.yml` 的目录即可。目前只做版本更新，不含安全更新；所有 GitHub 计划可用，GitHub Enterprise Server 要到 3.24。

  这条的分量在于它承认了一个事实：agent 的 skill 与 prompt 已经是依赖，需要锁版本、需要可审计的升级路径。之前靠 `git clone` 到 `.claude/skills/` 的做法，迟早要面对「谁在什么时候改了我的指令」。

## AI 技术

- **[Ai2 发布 StateBench：测模型在长文档里跟不跟得住状态变化](https://huggingface.co/blog/allenai/statebench)**（Hugging Face Blog / Ai2，11-03）

  基准把状态追踪分成四级：值不可变、按值重新赋值、自引用更新（`x = x + 5`）、按引用赋值（`x = y` 与交换变量，即 S₅ 问题）。结论有两面：专门在这些任务上训练的循环与混合架构（如 Gated DeltaNet）比 Transformer 外推得远得多；而 Gemini 3.8 Flash、Claude Opus 5.5、GPT-6 Sol 与 Luna 这些前沿模型，在更难的两级上仍会随输入变长而崩。

  对写 agent 的人这是可操作的信息：读代码、跟踪变量、多轮工具调用中的实体状态，恰好落在 Transformer 的弱项上，别指望靠加长上下文窗口解决；需要在外部维护状态，或把任务改写成「每步只取最新值」的形态。数据与代码已公开。

- **[LeanGuard：用 Lean4 证明过的策略约束每一次工具调用](https://arxiv.org/abs/2611.02332)**（arXiv，11-02）

  思路是把 domain policy 写成 Lean4 里的状态谓词加有时间范围的过去时算子，每次工具调用在进入环境前先过检查，判定过程被证明与 LeanLTL 语义等价，失败即拒绝（fail-closed）。结果：Tau-Bench 上五个 Qwen 模型（0.8B 至 27B）在无护栏时至少执行了 33 次策略禁止的调用，加护栏后为 0，任务成功率无显著变化；DTap 上直接 prompt 注入成功率从 57.9% 降到 5.9%。论文还给了「证明引导修复」：不用模型，用 Lean 元编程搜索一个满足策略且保留意图的相近调用。

  对要上生产工具的 agent，这是把「提示词里写别删库」换成机器可检查约束的一种做法；代价是要学 Lean4 并维护策略证明，适合动作空间稳定的场景。

- **[Qwen 3.8 27B 在笔记本上也能「读懂」模型权重](https://simonwillison.net/2026/Nov/3/qwen-can-interpret-model-weights/)**（Simon Willison's Weblog，11-03）

  这是前一日「权重空间编程」争议的后续实测：Simon Willison 用论文里的例子在本机跑 Qwen 3.8 27B，模型同样能从一堆浮点数里推断出网络在做什么。他把论文里混在一起的两件事拆开——模型不借助工具直接读权重，和模型写代码去改权重，是两种不同的能力主张；同时保留了 spaCy 作者 Matthew Honnibal 认为原论文误导的意见。

  需要注意这是单例、非系统评测，只能说明消费级模型也能做一部分，不足以支撑原论文关于大幅提升 MATH-500 的结论。

- **[CWE-bench v2：100 个真实漏洞修复任务，评分完全程序化](https://huggingface.co/blog/cwe-bench)**（Hugging Face Blog / Collinear AI，11-03）

  agent 拿到真实开源仓库的 checkout 和一句简短指令，要找出并修掉一个安全弱点且不破坏原有功能；评分靠预写的程序化检查，可复现、无额外成本，检查项经 LLM 评审校准过硬度和公平性。公开集 100 题，另有 held-out 集防止过拟合。

  对做 AI 代码安全评测的人，这是少见的「能自己跑、结果可复现」的基准；局限也清楚：程序化检查只覆盖能被断言的行为，真实漏洞「修得对不对」往往还需要人判断。

## 大前端与后端

- **[Next.js 11 月安全版本：一次修 7 个 CVE，含一个高危缓存越权](https://nextjs.org/blog/november-2026-security-release)**（Next.js Blog，11-03）

  升级到 16.4.5（Active LTS）或 15.5.29（Maintenance LTS）。高危项是 `unstable_cache` 与 `use cache` 混用时的跨租户缓存泄露：同一个 public `use cache` 函数既被直接调用、又被 `unstable_cache` 内部调用，且读到 root 参数（如租户 ID）时，冷缓存并发填充可能把另一个请求的结果写进缓存，再发给后续同参数的调用者。

  其余六个为中危，集中在 Cache Components 的嵌套缓存 root 参数、二进制参数造成的缓存键碰撞、自托管下的共享 shell 缓存投毒、陈旧压缩响应的分帧、Edge 路由内部响应头泄露 cookie、Image Optimization 的 SVG 校验绕过。如果站点开了 Cache Components 又用 root 参数分租户，这次按紧急升级处理。

- **[Safari 27.3 beta 引入 Adaptive Dark Mode：没做深色的站点也变深色](https://webkit.org/blog/18541/introducing-adaptive-dark-mode/)**（WebKit Blog，11-03）

  用户开启后，Safari 会分析页面配色，判断整体偏亮就自动转深色：用保色相的亮度反转矩阵，文字对比度按 WCAG 4.5:1 取目标；SVG 图标按需改色，位图只对简单黑白 logo 做直方图判断后反转；`<canvas>` 内容不动，部分 mask 与 `mix-blend-mode` 会被关掉以避免异常。声明了 `<meta name="color-scheme" content="light dark">` 或 `color-scheme: light dark` 的站点完全不受影响。

  WebKit 给的数字是：约 40% 的页面加载发生在深色模式下，只有 10% 的页面支持深色。对我这类站点，最低成本的动作就是补上 `color-scheme`，让浏览器的自动处理让位于自己的设计；否则用户看到的深色版本是浏览器猜出来的。

- **[Supabase MCP 支持企业托管认证，Claude 可以自己签发身份断言](https://supabase.com/blog/claude-issued-enterprise-managed-auth-for-mcp)**（Supabase Blog，11-03）

  原先的 MCP 企业托管授权要求 IdP 支持对应扩展，而目前只有 Okta 落地，多数 IdP 还没跟上。现在可以由 Claude 充当 issuer，签发只对 Supabase 有效的短时 ID-JAG（Identity Assertion JWT Authorization Grant），签发前核对成员是否仍在 Claude 组织内、以及其邮箱。效果是组织管理员批准一次，成员用现有 SSO 身份直接使用，不再逐人过同意页。

  Supabase 侧对配置了 SSO 的 Team 与 Enterprise 正式可用，Claude 侧的 auto-connect 还是 Team 与 Enterprise 的 beta。对做企业内部 agent 的人是路线提示：MCP 的授权正从「每个用户点同意」转向「组织级信任加快时断言」。

- **[Vercel CI 不再要求仓库关联 Vercel 项目](https://vercel.com/changelog/vercel-ci-no-longer-requires-a-linked-vercel-project)**（Vercel Changelog，11-03）

  此前要跑 Vercel CI 得先建一个空项目把仓库接上，现在只要装了 Vercel GitHub App、GitHub 账号已连接、并有仓库的 write 或 admin 权限，在 clone 里执行一次启用命令即可，任务按仓库里的配置运行。限制是仅支持私有 GitHub 仓库，公开仓库与其他 Git 托管还没支持。

  对已经在用 Vercel 但不想为一两个仓库单独建项目的团队，这减少了一次无意义的配置动作。
