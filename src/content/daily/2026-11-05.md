## 今日概览

截至今天 08:15（UTC+8），过去 48 小时最值得读的是一条被 HN 顶上来的旧闻复盘：PHP2Shell 的根因是一个 2024 年就报给 PHP 基金会的「内存不足」缺陷，因为「只会让程序崩溃」被搁置，直到 AI 辅助审计把它变成远程执行代码。这背后是一个结构性变化——找漏洞的成本在下降，修漏洞的成本没有。

模型侧同一天发生两件事：Kimi K3.1 Pro 以 2.8T 总参数、104B 激活的 MoE 开放权重，附带一份带商用门槛的自定义许可；Ripple-65B 用 3200 万美元训练成本在 TerminalBench 2.1 上刷到 80.52。工程侧，Go 1.27 把 `encoding/json/v2` 转正，Node.js 则预告 11 月 11 日发三个版本线的高危安全版本。

## 行业动态

- **[PHP2Shell 是一次警告：AI 正在逼我们还 40 年的技术债](https://spectrum.ieee.org/ai-in-cybersecurity-php2shell-vulnerability)**（IEEE Spectrum，11-02；HN 讨论 11-04，1023 分）

  10 月下旬披露的 PHP2Shell 影响 WordPress、Drupal 等一大片站点，包括 NASA、维基百科和白宫的网站，漏洞能读数据也能在服务器上执行代码。它的根因并不新鲜：一个内存分配不足导致的崩溃缺陷，2024 年就报给了 PHP 基金会，因为「只是崩溃」而一直没修。今年安全公司 Calif 在 OpenAI 赞助下独立审计 PHP，一名研究员借助 AI 工具在两周内把崩溃变成了任意代码执行，Wiz 随后确认并扩展了利用面；基金会四名工程师用两个月做补丁，抢在被利用之前发布。

  这条值得读的地方不在「AI 攻击」这个标签。Tolmo 的 AI 安全研究负责人 Matt Suiche 说的是：过去 40 年由人写的遗留软件正在被集中暴露，现在是偿还技术债的时候。哥伦比亚大学的 Suman Jana 补了另一半：找 bug 和修 bug 存在根本不对称，修的时候要确认每条攻击路径都堵上、还不能破坏现有功能。对运维 WordPress 或跑老 PHP 服务的人，这条的实际动作只有两个——确认补丁已上，以及把「只是崩溃」的报错当成待修缺陷而不是噪音。

- **[C++26 的 DIS 投票未通过，卡在 contracts](https://andreasfertig.com/blog/2026/11/cpp26-dis-failed-how-does-cpp-survive/)**（Andreas Fertig 博客，11-03；投票日 10-23）

  作者是 WG21 成员、代表德国投票。据他记录，10 月 23 日结束的 12 周 ISO 国家成员体投票结果为「不通过」，未达到所需的三分之二多数，理由集中在 contracts 这一特性尚未准备好发布。这是 C++ 历史上第一次 DIS 表决失败，可比的只有 2006 年的 C++/CLI 规范，那个项目最终被终止。他也说明 ISO 规则不允许公开票数分布，文中观点属个人。

  对写 C++ 的人，实际影响是 C++26 的时间表要往后挪，而 contracts 的语法和语义在最终定稿前不宜押注。它也提醒一件事：把一个语言的正式标准当作稳定 API 来规划多年项目，风险比想象中大。

- **[Cloudflare 上线 Zero Wire：给关键漏洞做一份「新闻电讯」](https://blog.cloudflare.com/zero-wire/)**（Cloudflare Blog，11-03）

  Zero Wire 挂在 Cloudflare Radar 的安全板块下，是一条公开的漏洞情报流。每份简报包含一段不带术语的解释、谁该去查、建议动作，以及指向厂商公告和技术细节的链接，另外提供一段预置 prompt，可以直接喂给 agent 评估自己基础设施的暴露面。官方明确说它不追求覆盖所有 CVE，只挑互联网暴露软件里的关键漏洞。

  它给出的动机正好接上一条 PHP2Shell：AI 让漏洞发现的速度和数量都在上升，安全团队需要一个能快速判断「我有没有中」的入口。免费、不要求是 Cloudflare 客户，值得在下次高危 CVE 出来时对照着看一次。

## 产品发布与更新

- **[Vercel Security Review 进入公测](https://vercel.com/changelog/vercel-security-review-public-beta)**（Vercel Changelog，11-03）

  面向 Pro 和 Enterprise 团队，开启后每次推送到已连接的 GitHub 仓库都会自动做漏洞审查，结果进 Vulnerabilities 面板。每条发现记录项目、环境、分支和 commit，附带摘要、修复建议和 AI 生成的严重度评级。它挂自己的 GitHub check，有 PR 时还会把发现贴成 review comment；公开仓库的细节只留在面板里，不进评论。

  一个容易被忽略的设计是触发条件用 push 事件而不是 PR，所以直接推和 force push 到生产分支也会被审。修复路径有两条：点「Fix with Vercel Agent」让它提 PR（合不合由你定），或者在 CLI 里跑 `vercel security vulnerabilities`、把发现导出成 Markdown 交给自己的 agent。AI 给的严重度评级仍需要人复核，公测阶段更适合当第二道网而不是唯一一道。

- **[Workflow SDK 的 start() 支持原子化幂等启动](https://vercel.com/changelog/atomic-start-hooks-in-the-workflow-sdk)**（Vercel Changelog，11-04）

  现在 `start()` 可以在一步原子操作里同时接纳一次运行并占用一个 hook，重复启动会安全失败并抛 `HookConflictError`。这替换掉了此前 `getHookByToken()` 再 `start()` 的写法——那两步之间的空隙本身就是官方文档承认的重复启动竞态。被占用的 hook 从运行被接纳的那一刻就存在，所以 `resumeHook` 在运行真正开始执行前也能工作，早到的 payload 会按顺序缓冲后投递。

  对做 agent 工作流的人，这省掉了一张自建的幂等表：典型的场景是支付回调或 webhook 重复投递，你现在可以「第一次开跑、后续把 payload 转给已存在的 run」，不用在应用层再锁一次。

- **[GitHub Copilot 进入 Xcode 内置的编码助手](https://github.blog/changelog/2026-11-04-github-copilot-is-now-available-in-xcodes-coding-assistant)**（GitHub Changelog，11-04）

  公测阶段，需要 Xcode 27.3 beta 和 macOS Tahoe 26.6 以上，在 Xcode 的 Settings > Intelligence 里配置，所有 Copilot 套餐都支持。原有的 Copilot for Xcode 扩展仍然独立存在，两者可以按习惯选。官方没有说明它在 Xcode 里能调用哪些模型、上下文范围有多大。

  这条对我的直接价值不大，但方向值得记：Copilot 正在从「装一个插件」变成「成为 IDE 自带的助手」。当 IDE 厂商自己提供 agent 入口时，第三方插件的差异会越来越集中在上下文管理和团队策略上。

- **[Cloudflare 让你看见「谁家的 agent 在访问你的站」](https://blog.cloudflare.com/personal-agents-visibility-control/)**（Cloudflare Blog，11-04）

  Security Analytics 的 Bot Analysis 图里新增 Personal Assistants 分类，可以和已验证机器人、疑似人类等并列筛选；Top statistics 里新增一个小组件，列出是哪些个人助手在访问、各发了多少请求，点开单个 agent 后其余图表会跟着过滤，能看到它请求了哪些路径、拿到什么状态码、从哪些网络来。处于早期访问的 Account Abuse Protection 还能看到每个 agent 代表哪个用户，登录和注册事件现在会标记请求是否来自 agent、来自哪一个。

  同时，原有的 Agents 策略扩展到对受支持的个人助手做更细的准入控制。对做带账号的站点的人，这意味着 agent 流量可以当成独立人群来运营：结账和登录流程要不要放 agent 进来、进来后走哪条风控，是可以分开决策的，而不是整体拉黑。

## AI 技术

- **[Kimi K3.1 Pro 开放权重：2.8T 总参数、104B 激活、1M 上下文](https://huggingface.co/moonshotai/Kimi-K3.1-Pro)**（Hugging Face 模型卡，11-02；HN 讨论 11-04）

  Moonshot 把 K3.1 系列第一款模型放了出来，原生多模态，从 K3 出发做了覆盖数百个下游领域的联合强化学习。总参数 2.8T、激活 104B 的 MoE，上下文 100 万 token。按模型卡自带的对比表，Terminal-Bench 4.0 拿到 65.7，略低于 Claude Opus 5.5 的 66.4；SWE Marathon v1.1 是 51.7，高于 Opus 5.5 的 46.3 和 GPT-6 Astra 的 42.5；但 Program Bench 只有 31.5，明显低于 Claude Fable 5.1 的 53.5。这张表是厂商自己跑的，横向比较只能当参考。

  许可比参数更值得看。它叫「Kimi K3.1-Pro License」，允许使用、修改、分发、微调甚至售卖，但两条商业条款要注意：如果你或关联方在任意连续 12 个月里做模型即服务且合计营收超过 2000 万美元，必须单独和 Moonshot 签协议；如果用于月活超过 1 亿或月营收超过 2000 万美元的商业产品，界面要显著标注「Kimi K3.1-Pro」。内部使用和通过官方或认证推理伙伴的调用不受这两条约束。

  对个人开发者，实际结论是：权重是真开放，但 2.8T 的体量自己部署不现实，走 API 或第三方推理服务更合理；真要基于它做产品，先把许可第 2、3 条读完。

- **[Ripple-65B Preview：650 亿稠密模型，宣称美国开放权重在 agentic coding 上的 SOTA](https://www.ricursive.com/ripple)**（Ricursive Intelligence，11-04）

  这家做芯片设计的实验室从零训了一个通用版本：650 亿参数稠密架构，12 万亿 token 预训练，支持 100 万上下文。在 TerminalBench 2.1 上拿到 80.52，超过了一批参数量大得多的美国开放权重模型——Reflection Beam 501B 的 80.1、Meta Muse Spark Open 816B 的 76.4、Thinking Machines Inkling 975B 的 63.8。他们强调 RL 只用了 140 万次 rollout，约为上一任 SOTA 的七十分之一，全部研发成本 3200 万美元。

  稠密小模型的好处是可落地：官方点名能在 DGX Spark 这类显存带宽不高但算力不低的设备上跑。已上 Hugging Face、Together AI、GMI Cloud 和 OpenRouter，Fireworks 当天稍晚跟进。仍要打折看：这是 Preview 版本，所有数字都是厂商自测，第三方复现之前不宜据此改选型。

- **[Anthropic 让「这个回答确实来自这个模型」可以被证明](https://www.anthropic.com/research/provable-inference)**（Anthropic Research，11-02）

  问题很具体：你今天调用一个模型，无法验证返回结果真来自声称的那个模型，而不是被路由服务为了省钱偷偷换成了便宜的，或者被中间人改过 token 流。Anthropic 的方案是基于 zkSNARK 的推理证明——提供方先对模型做承诺，再证明每条回答都由该模型产生，权重保持隐藏，架构不隐藏。

  性能数据：在 Llama 4 Maverick（400B MoE）上，单张 H100 的证明生成速度约 110 token/s，每 1024 token 请求的证明约 19MB，权重为 4 位量化、prefill 用整数运算；这个开销大约是直接把模型跑在 vLLM 上的 70 到 95 倍 GPU 时间。他们放了五个产物：技术报告、协议规范（Claude 写的）、prover 加两个 verifier（C++ 快速版和 Lean 可证明正确版）、Lean 证明，以及一个可视化审阅工具，全部 Apache 2.0。

  70 倍开销意味着它现在不适合交互式推理，但适合审计和对账：批量任务结束后抽验一批回答、或者给监管和客户证明「你拿到的确实是这个模型」。对做路由层的人，这是把「我们不会偷换模型」从承诺变成可验证的一步，代价是延迟和成本。

- **[LoCo：让模型自己判断「这里不必再想了」](https://huggingface.co/papers/2611.04814)**（Hugging Face Daily Papers，11-03）

  推理模型的成本大头是思维链太长——信息够了还在继续推演。已有压缩方法多在整条轨迹上做裁剪，这篇把决策下沉到局部：从模型自己的轨迹里识别「过度思考」状态，冻结该状态之前的推理前缀，从同一状态重新生成更短且通过验证的续写，再用这些样本做偏好学习。

  它解决的是工程上很实际的问题：同一道题，能不能在正确率不掉的前提下少烧 token。目前只有论文摘要可读，评测范围和独立复现都还没有，暂不当成可直接上线的方案，但「在轨迹中间判断是否继续」这个思路可以借到自己的 agent 循环里——比如给工具调用加一个「信息是否已足够」的判定点。

- **[Nvidia RTX Spark 笔记本装 Linux：GPU 被锁在 780MHz](https://www.mindstudio.ai/blog/linux-nvidia-rtx-spark-laptop)**（MindStudio 实测，11-01；HN 讨论 11-04）

  实测机型是 MSI Prestige N16 Flip AI Plus。Linux 能装、桌面正常、开源内核驱动能加速、4K 120Hz 和音频触控板都能用，但插电后 GPU 被锁在约 780MHz，Windows 下是 2.2GHz 以上。原因是负责 CPU 与 GPU 之间供电调度的 Nvidia Platform Controllers and Framework 只有 Windows 版，其电源表加密，Linux 读不到。用 GPT-OSS-120B 实测：Windows 65.4 token/s、WSL 65.1、DGX Spark 61、原生 Linux 只有 13.9。另一个坑是这台机器默认给 GPU 划走 96GB 统一内存，而只有 Windows 提供调整这个切分的设置。

  测试条件很窄——一台机器、一个模型，不能推广成「所有 Spark 设备在 Linux 上都慢」。但对考虑用这类设备做本地推理的人，结论够清楚：现阶段 WSL 比原生 Linux 划算，双系统不是免费的。

## 大前端与后端

- **[Go 1.27 转正 encoding/json/v2：默认拒绝非法 UTF-8 和重复键](https://go.dev/blog/jsonv2)**（Go Blog，11-04）

  `encoding/json/v2` 和 `encoding/json/jsontext` 在 Go 1.27 里稳定并正式可用。v2 放在独立的命名空间，`encoding/json` 本身不变，所以可以按调用点或按类型逐步切换，不要求一次性迁移。

  修掉的老问题清单很实在：默认拒绝非法 UTF-8（RFC 8259 要求），默认拒绝重复成员名（这类歧义被利用过，参见 CVE-2017-12635），nil 切片和 map 默认序列化成 `[]` 和 `{}` 而不是 `null`，默认区分大小写匹配字段名，指针接收者的 `MarshalJSON` 调用行为一致，选项可以作用于 `Marshal`/`Unmarshal` 而不只是 Encoder/Decoder。性能上，Marshal 与 v1 基本持平，Unmarshal 官方给的基准最多快 10 倍，前提是把自定义的 Marshaler/Unmarshaler 迁到 `MarshalerTo`/`UnmarshalerFrom`。

  对写 Go 服务的人是少踩坑的机会：重复键和大小写不敏感匹配这两条，过去是接口对账和安全审计里反复出现的争议点，现在有默认安全的选项，代价是行为变更要在升级时逐个确认。

- **[Node.js 将于 11 月 11 日发布三个版本线的安全版本，最高等级 HIGH](https://nodejs.org/en/blog/vulnerability/november-2026-security-releases)**（Node.js Blog，11-03）

  官方公告：26.x、24.x、22.x 三条线会在 11 月 11 日（周三）或稍后发布新版本，每条线修复的最高严重级别问题都是 HIGH。公告没有透露漏洞细节，这是常规做法——在发布前不公开，避免提前暴露。EOL 版本在每次安全发布时同样受影响，官方提示按发布计划升级到受支持版本。

  实际动作是先把升级窗口排进日程：三条线同时发 HIGH，说明问题大概率在共用代码路径上。跑 22.x 的项目要确认它还在维护期内，别等到当天才发现自己用的是 EOL 分支。

- **[Supabase MCP 支持由 Claude 签发身份断言](https://supabase.com/blog/enterprise-managed-auth-for-mcp)**（Supabase Blog，11-03）

  企业在接 MCP 时通常卡在身份上：默认每个成员用自己的账号登录、在同意页逐个授权，而企业级托管鉴权要求身份提供方支持 MCP Enterprise-Managed Authorization 扩展——目前基本只有 Okta 支持。新方案让 Claude 自己签发那个短期的 ID-JAG 断言：组织所有者或管理员批准 Claude 并把它注册为 issuer，之后所有具备匹配 SSO 身份的成员直接用现有角色访问，不再有逐人同意页。Supabase 侧已对配置了 SSO 的 Team 和 Enterprise 组织正式可用，Claude 的自动连接还在 Team/Enterprise 的 beta。

  官方把限制写得很清楚，这点值得表扬：Claude 签发时不确认你在身份提供方处是否真的登录、不检查多因素认证、也不套用 Supabase 自己的登录规则；Supabase 只校验签名对应的 issuer、成员是否属于组织且 SSO 身份匹配、以及管理员是否批准过。

  换句话说，接入摩擦下降的代价是把信任前移到了 Claude 这个 issuer 上。对安全要求高的团队，需要判断「Claude 组织成员身份」是否足以代表「公司员工身份」——这两者并不总是等价。
