## 今日概览

截至今天 08:00（UTC+8），过去 24 小时的主线是「代理写出来的东西」和「拒绝代理的地方」同时出现。AWS 发布本地云模拟器，公开说覆盖 438 个 API 模型、200 多项服务，代码全部由自主智能体编写，团队没有编写也没有审阅一行，靠的是保真测试、合并门禁与对抗式安全审查顶上；同一天，美联航把「AI 代理不得订票」写进运输合同，成为第一家把反代理条款落到法律文本的美国航司。开源侧则在收窄入口：一份持续维护的清单列出了二十多个明令禁止 AI 生成贡献的项目，其中包括 yt-dlp、immich、QEMU 与 Zig。

这两件事放在一起看，边界比结论更有用：能形式化描述、能用测试判定的活儿，已经可以整段交给代理；涉及身份、凭据与法律责任的环节，业务方反而在加固闸门。工程侧今天也有硬东西——Node.js 一次修掉 7 个高危漏洞，其中一个能泄漏 TLS 私钥。

## 行业动态

- **[AWS 发布本地云模拟器，代码由智能体写、团队未审阅一行](https://www.aboutamazon.com/news/aws/how-autonomous-ai-agents-built-aws-emulator)**（Amazon，11-11）

  工具本身很实用：在本机起一个 HTTPS 端点，把 AWS CLI 或任意 SDK 的 endpoint 指过去，就能在没有 AWS 账号、没有真实资源的情况下跑集成测试，覆盖 200 多项服务、438 个 Smithy API 模型。Linux 有 deb/rpm，macOS 与 Windows 走 Docker，Rust 测试可以把它作为 dev-dependency 内嵌进程，每个测试一个隔离实例。源码在 [aws/aws-emulator](https://github.com/aws/aws-emulator) 以 CC0 发布（vendor 目录为 Apache 2.0），不收 PR，缺口清单公开在 `things-that-do-not-work` 目录。

  更值得记的是做法。项目 9 月 11 日建仓，上线时约 2.97 万次提交、322 个 release；三组智能体分工——第一组按 API 模型写真实验收场景并对着真实 AWS 校准，第二组回放测试、把不符合的行为开成 issue，第三组一个 issue 一个代理去修，每次合并都要过编译、编码规范、安全对抗审查与保真回归四道门禁。高级首席工程师 Matthew Goldberg 的原话是团队没写也没审代码，同时他也承认「周末 demo 不是产品」，真正的工程量在门禁上。外部没有任何独立审计验证过这个说法，应按厂商自述对待。

  限制写得比宣传清楚：未实现的操作返回 501 而不是伪造成功；不模拟限流、故障与区域差异；不校验 IAM 策略，本地放行的请求到线上可能被拒；不对运行的代码做沙箱隔离。第三方有人下载 release 里的 fidelity 分数统计出 4.29 万个测试单元通过率约 56.5%、步骤级 73.2%，口径自定，但比「AWS 在你的笔记本上」这句更接近实情。

- **[美联航把「AI 代理不得订票」写进运输合同](https://www.cbsnews.com/news/united-airlines-bans-ai-agents-booking-flights/)**（CBS News，11-11）

  11 月 11 日修订的运输合同新增 Rule 6.J.6，禁止用 AI 代理「创建、修改或服务机票，以及购买任何产品或服务」，Rule 1 对 AI 代理的定义覆盖任何代表旅客行事的自主或半自主软件，有没有人盯着都算；配套的 Rule 5.H 允许美联航不经通知取消由代理下单的订单。范围同时覆盖自有网站 App 和旅行社、聚合平台这些间接渠道。检索与比价不受影响，被禁的是成交这一步。

  官方理由是凭据外泄、误购与里程被用，以及联邦法规要求旅客本人确认行李不含违禁品，代理无法代为履行。CEO 斯科特·柯比说得更直白：「坦白说，我不想再创造一个中间商。」西南航空的做法相反，把航班库存接进 ChatGPT 供查询；亚马逊此前已阻止 Meta 的 Muse 代用户购物，大通也在 10 月 27 日生效的协议里禁止第三方 AI 用客户凭据访问账户。做 agent 产品的人要注意：这条线的划定权在业务方手里，不在协议层。

- **[一份清单在统计「对 AI 贡献说不」的开源项目](https://osssaysno.com)**（Open Source Says No，11-11 见于讨论）

  站点逐条收录明令禁止 AI 生成内容进入贡献的项目，附政策原文、覆盖范围（代码 / 文档 / issue / 美术 / 翻译）与最后核对日期。目前列出的二十多个项目里有 yt-dlp（20.6 万 star，禁止 LLM、agent 参与任何形式的贡献）、immich（11.8 万）、meilisearch（5.9 万，明确不接受 Copilot、Claude Code、Cursor 生成的内容，含 PR 描述与评论）、okhttp、Servo、QEMU、Gentoo、Zig、stb、MonoGame。

  这是第三方整理，不是权威统计，也不能反推「开源界在集体抵制」。但它确实记录了一种现实压力：当代理能低成本批量提交 PR，维护者的评审带宽成了新的稀缺资源，于是干脆在入口处设卡。对习惯让 agent 直接开 PR 的人，这是一份应该先查再动手的名单。

- **[Python 社区纪念 Tim Peters（1952–2026）](https://discuss.python.org/t/in-memoriam-tim-peters-1952-2026/110028)**（Python Discourse，11-11）

  Guido 在帖中公布，Tim Peters 已于今年 7 月 15 日去世。他写下了 PEP 20（Python 之禅），贡献了 timsort 与 doctest，最早说服 Guido 让 int 与 float 支持混合算术；在邮件列表年代以「Timbot」闻名，答复里常带 `<wink>`。帖子 11-11 才发布，事件本身发生在四个月前。

  值得读的是 Guido 对早期核心开发氛围的描述：不轻易否定别人，把差异讲清楚。这种「评审文化」在今天被代理放大的提交量面前，反而更像稀缺品。

## 产品发布与更新

- **[n8n 推出 Nod：带自己电脑的开源个人代理](https://blog.n8n.io/meet-nod)**（n8n Blog，11-10；11-11 登上 Product Hunt 当日第二）

  Nod 是 n8n Labs 的研究预览，独立于 n8n 主产品，装在 Mac 或 Windows 上，不需要 n8n 账号。它有一台本地沙箱里的「自己的电脑」和自己的浏览器，因此能做完聊天助手只能列成待办的事：退订并拒绝挽留方案、盯价、登录没有 API 的供应商门户下载发票。对话可以走 App、Telegram 或 WhatsApp，多个任务并行，重复任务可定时。

  值得关注的是三处工程设计。记忆上它报 LongMemEval 93.2%，并会把「上次怎么做的」写下来复用、站点改版后再修正；安全上发送、付款、发布、删除前有一次独立的模型审批，但 n8n 自己说明这个审批也是模型、会出错，凭据存在本机并用模型读不到的私有表单输入；成本上每个任务结束给一张回执，可设月度上限，单任务超过 5 美元会来问。限制很实在：笔记本休眠就停，一套安装只有一个主人，不能打电话，macOS 14+、Windows 11 还是预览。免费，Apache 2.0，模型钱自己付，也可以接本机开源模型。

- **[ElevenLabs 发布 Scribe v3 与 v3 Live](https://elevenlabs.io/blog/scribe-v3)**（ElevenLabs Blog，11-10）

  两个模型分工明确：Scribe v3 处理录音，在 102 种语言上比 v2 少 27% 词错，三人以上会议的说话人分离错误少 17%；Scribe v3 Live 走实时，比 v2 Realtime 少 43% 错误，第一次在实时转写里带上说话人分离（比次优实时模型少 39% 错误）。定价 $0.22/小时，所有套餐一致，API 里换模型 ID 一行即可。

  真正解决问题的不是分数而是轮次判断：v3 Live 用对话上下文而不是单纯静音时长来决定「对方说完了没有」，所以读到一半停一下报号码不会被切断。另有 keyterm prompting（最多 1000 个术语）与 keyterm library（最多 10 万个，只在听到疑似匹配时查），对塞满品牌名和药品名的场景比通用识别靠谱。中文支持在 90 多种语言里，但官方基准以 FLEURS 的短句朗读为主，真实嘈杂环境仍需自测。

- **[CALL-E：给 AI 代理一条能打电话的线路](http://www.heycall-e.com/)**（CALL-E 官网，11-12 在 Product Hunt 榜单）

  背后是 AI Rudder，做法不是「一句话拨号」，而是把不可逆动作拆成三步：先追问缺失信息，再给出通话计划（目标、开场、要问什么、被拒怎么办），确认后才真正拨号。它能自己走 IVR 按键菜单、等人工、留言，结束后返回结果、摘要和逐字稿——对改约、报价、投诉这类需要留证的场景，逐字稿比摘要更有用。

  接入方式给了 SDK、API、CLI、MCP 和 skill，可以塞进 Claude Code、Cursor 这类工作流，把「打电话」变成一次工具调用。计费分两段：通话费按 10 秒计（含运营商与模型成本），成功费只在目标真正达成时收，餐厅只是接通不算成功；新用户 100 额度。号码多为平台购买或走 SIP，外呼需要 KYC，多数地区不能直接绑定个人手机号。适合先拿一个低频、结果可验证的场景试，别一上来就接付款类流程。

## AI 技术

- **[Google 推出 Gemini Decisions API 与 Decision 1 模型](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-decisions-api/)**（Google，11-11）

  这是「决策模型」这条线上第三家正式入场的：输入一段多模态上下文（文本、图像、音频、视频、PDF，最多 256K token）加最多 1000 个独立问题，模型不做逐 token 生成，而是在一次前向里给候选答案打分，返回概率与置信度。支持三类问题：是/否、2–255 选一、有序 rubric 打分。延迟 150–250 ms 端到端，中位模型计算 50–100 ms，$0.10/百万输入 token，输出不计费。

  对工程的意义是省钱和省事：路由、分级、策略检查这类活不需要可读文本，只需要一个能设阈值的分数，拿它替掉一次生成式调用，官方称在共享基准上比 Gemini 3.5 Flash-Lite + Interactions API 便宜近 5 倍。Simon Willison 拿视频实测，是/否问题返回的是 0.0497、0.9234 这样的概率而不是干脆的 0 或 1——这既是校准更好的证据，也意味着你的代码必须处理「不确定」这一档，别把它当布尔值用。

- **[Apple 把最大内积搜索改写成「学一个支撑函数」，RAG 检索快约 8 倍](https://machinelearning.apple.com/research/faster-retrieval)**（Apple Machine Learning Research，11-11）

  思路很省：文档库是固定的、查询分布在生产里通常是稳定的，那就可以离线训练一个小网络，把「这个 query 最该去哪个簇、最像哪个 key」记住，而不是每次现场算几何距离。两个模型各有用途——SupportNet 学的是集合的支撑函数，用来替代质心路由（质心看不出簇内分布，离群点会被跳过）；KeyNet 直接把 query 重写成预测的最佳 key，插在标准 IVF 索引前面，不动索引本身。

  在 Natural Questions（约 260 万段、128 簇）上，SupportNet 达到 95% 路由召回时比质心路由快约 1.9 倍（1.74 ms vs 3.36 ms，已含网络开销）；KeyNet 达到 99% 召回时耗时降到约 1/8（0.23 ms vs 1.8 ms）。前提也明确：查询分布要已知或稳定，要一次性付出离线采样与穷举标注的成本，评估主要基于 FAISS IVF 与单一大数据集。适合文档库固定、QPS 高的 RAG，不适合查询天天变的场景。

- **[给智能体的记忆加上「证据链」，减少越记越差](https://huggingface.co/papers/2611.14320)**（arXiv 2611.14320，11-10）

  论文指出一个反直觉现象：外部记忆能让 agent 从经验里学，也会让它在本来能做的任务上失败——因为一条从「成功/失败」二值标签里蒸馏出来的经验，可能本身就是错的，或者被误用、误读，而记忆系统只给结论、不给来源，模型无从核对。作者的做法叫 WikiTrace：每条经验都连到一个「这条轨迹为什么成功/失败」的摘要，再连到原始轨迹；新任务先铺开所有经验，遇到缺细节或互相冲突时回溯原始轨迹去查。

  这对做 agent 记忆的人是一个明确的接口建议：记忆条目不要只存一段话，要能追到产生它的那次执行。论文同时给了一个可用的判断依据——轨迹里往往还留着能识破错误经验的那点证据。

- **[0.8B 的端侧代理模型 BotPsy：工具调用可以很小](https://huggingface.co/blog/qvac/botpsy)**（Hugging Face Blog，11-11）

  基座是 Qwen3.5-0.8B，专门做函数调用与 agentic 工作流微调。结果比预期扎实：BFCL v4 从 23.4 到 44.0，τ-bench 从 23.2 到 51.5，ACEBench 从 30.1 到 58.7，IFEval 从 59.7 到 90.8；在与 ≤1.2B 模型的对比里六项基准拿下五项，BFCL v4 上甚至超过 2.5 倍大的 Qwen3.5-2B-Think。

  更值得注意的是「知道不该动手」：BFCL v4 的幻觉测试（没有合适工具时应当拒绝）得 86.1，为参测最高；ACEBench 的特殊情况（请求不完整、参数错、工具无法满足）从 13.7 升到 51.3。红队测试里不安全回答率 21%（基座 36%），提示注入下从 46% 降到 31%。作者自己划了线：仍会出错，不适合高风险用途，指令一多性能就掉，低资源语言明显落后。适合端侧做「低中难度、动作明确」的助手，不适合当通用代理。

- **[一线工程师复盘：全量用 AI 写码后，代码库变脆了](https://evanxmerz.com/post/ai-usage-generates-a-fragile-codebase/)**（个人博客，11-07；11-10 在 Hacker News 引发 600+ 条讨论）

  作者给出四个机制：AI 爱写浅测试（大量 get/set 覆盖，e2e 只走已有路径，行覆盖率看着漂亮但盲区不可见）；爱过度抽象（一个能解决的问题拆成三个 helper，为了 DRY 牺牲可读性）；人越来越不懂自己的代码（改不动、看不出新抽象与既有结构冲突）；提交速度超过评审速度（只能扫读，小问题累积成意大利面）。

  他也列了四个症状：事故变多、恢复变慢、错误只在真实用户那里出现、产品体验退化。这是个人观察，样本是自己待过的两家大厂，不能当统计结论；但「评审带宽是瓶颈」这个判断，和上面 AWS 用门禁替代人工审查、开源项目直接禁止 AI 贡献，指向的是同一个瓶颈。

## 大前端与后端

- **[Node.js 11 月安全版一次修掉 7 个高危漏洞，其中一个能泄漏 TLS 私钥](https://nodejs.org/en/blog/vulnerability/november-2026-security-releases)**（Node.js，11-11）

  已发布 26.13.1、24.22.3、22.23.5，共 16 个 CVE：7 高危、6 中危、3 低危，同时升级了 llhttp、undici、sqlite 依赖。最该立刻处理的是 CVE-2026-123864：HTTPS 上零长度的 TLS 写会重入 `llhttp_execute()`，服务端把自己堆里的内存当成请求体拷进响应，可能带出其他连接的请求乃至 TLS 私钥。触发条件是「先 `res.flushHeaders()` 再在请求体结束前 `res.end(chunk)`」，外加任意回显请求体的路由——这在这类实现里并不罕见。明文 http 不受影响。

  其余高危覆盖 HTTP/2 与 TLS：会话析构时的断言 abort（CVE-2026-123863，2024 年那个洞的变体）、关闭期间协议错误导致的会话与 fd 永久泄漏（123865）、流拆除时的 use-after-free（123866）、`respondWithFile()` 流被 reset 时的 UAF（123874）、TLS 延迟回调在 socket 已销毁后执行导致进程崩溃（126051，用了 `SNICallback`、`OCSPRequest` 等钩子的服务要注意）、以及 TLS 1.2 重协商改 servername 绕过按主机名区分的客户端证书策略（123872）。

  其中两个由 Chris Rohlf 与 Anthropic Research 合作发现，修复主要出自 mcollina。这类洞的共同点是「默认配置就能被打」，如果服务直接暴露在公网且跑 22/24/26 任一线路，今天就该排升级。

- **[Cloudflare 为全球控制面选了「无主」共识算法 QuePaxa](https://blog.cloudflare.com/choosing-quepaxa/)**（Cloudflare Blog，11-11）

  Meerkat 是 Cloudflare 内部管理全球控制面的 KV 服务，副本跨洲部署。常规共识算法（Raft、Multi-Paxos、VR）都依赖一个 leader，leader 一慢、一断、一换，整个系统就跟着降级——他们吃过这个亏：2020 年一个核心交换机故障让某共识系统退化，面板比平时慢 80 倍，持续六小时，数据没丢但写操作不可用。

  换到 QuePaxa 的理由是它不靠 leader 推进，因此绕开了两处脆弱点：多 proposer 相互抬 ballot 造成的「破坏性干扰」，以及依赖超时判断故障带来的误判。代价要说清楚：这是较新的算法，成熟实现少，运维与调优经验都不如 Raft 厚。文章把 Paxos 的两阶段、破坏性干扰、以及 QuePaxa 如何保证活性讲得比较透，适合想补分布式共识的人读。

- **[Firefox 把指纹识别的地基拆掉一层](https://blog.mozilla.org/security/2026/11/10/open-research-stronger-privacy-making-firefox-users-harder-to-fingerprint/)**（Mozilla Security Blog，11-10）

  结论来自一篇被 CCS 2026 接收的论文，测量面很大：近 2500 万 Firefox 用户的遥测，用 OHTTP 中继把 IP 与内容分离，只保留聚合结果。核心发现是效率很高——只保护少数几个特征，就能显著削弱 Fingerprint Pro、Signifyd、Akamai 这几家常用指纹方案的分辨能力。

  具体做了两件事：限制屏幕分辨率 API 暴露的信息，把任务栏或 Dock 的尺寸与位置藏起来；把 CPU 核数只报成 4 或 8，而不是精确值。目标不是让指纹失效，而是让更多用户「看起来像同一群人」。部分保护（如隐藏任务栏尺寸）默认开启，其余先在隐私浏览与严格 ETP 下灰度，最新一批随 Firefox 145 发出。做前端埋点或风控的要留意：拿屏幕尺寸、核数、Web Audio、Canvas 做设备标识的做法，在 Firefox 上的稳定性会继续下降。

- **[五个 Web 开发者用 Expo 做出 1.7 万行 Swift 的 iOS 键盘扩展](https://expo.dev/blog/supernova-ios-keyboard-extension-expo)**（Expo Blog，11-11）

  印度团队 Supernova 的产品是英语口语练习 App，三个 App 共用一套 TypeScript 代码（React Native + React Web + Node 后端，部署在 Vercel 与 Cloudflare），累计 2600 万下载、350 万月活，在印度 Google Play 进过前十。他们没写过原生 iOS/Android 代码，iOS 键盘扩展约 1.7 万行 Swift，初稿由 agent 起草，再靠真机遥测定位问题，全程没离开 Expo。

  这篇的价值不在「AI 写代码」，而在取舍：哪些必须下沉到原生（键盘扩展、Android 小组件），哪些留在共享包（电话自动填充、订阅与结账、埋点），以及怎么用真实设备数据替代模拟器里的自测。属于团队自述的工程复盘，条件是他们自己的用户结构，不能直接推广到所有 RN 项目。
